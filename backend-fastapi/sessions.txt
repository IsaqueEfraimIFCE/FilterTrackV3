Architecture summary
- Single Fly Machine, single SQLite DB on a Fly volume.
- Fly volume is NOT replicated — backups are the user's responsibility.
- SQLite is configured with foreign_keys=ON, busy_timeout=5000, WAL + synchronous=NORMAL.
- Postgres was intentionally dropped (psycopg removed). Models use plain SQLAlchemy JSON.

Reasoning kept on file:
- SQLite-on-volume is the chosen low-cost path for one backend instance with modest write load.
- Move to Postgres only when we need: multiple writers, HA/failover, managed backups, or
  multi-machine scale-out.


Canonical storage contract (Android <-> backend)
- Stored session JSON keeps: session/device/filter source facts, filter.station,
  optional filter.custom and createdAt.
- Stripped on the way in: flow10sLpm, flow60sLpm, flowSessionLpm, direction, isoTime
  (when ts is present), sampleCount (computed from samples).
- sample_count column is computed from the stored samples, not trusted from input.
- filter_station column was added; startup runs an ALTER TABLE migration for older DBs.

Compact sample format (distance_cm_x100_v1)
- 100 ms BLE samples for 10+ minute sessions are stored as parallel arrays, not objects.
- Shape:
    samples = {
      format: "distance_cm_x100_v1",
      t0: <first ts in ms>,
      dtUnit: "ms",
      distanceUnit: "cm",
      scale: 100,
      t: [offsetMs, ...],
      d: [distanceCm * 100, ...]
    }
- d=2428 means 24.28 cm.
- Backend accepts both legacy list samples and compact samples; legacy is converted to
  compact before storage.
- Size: 6000 samples ~71 KB compact vs ~240 KB object-per-sample (~70% smaller).
- Live flow/direction UI is computed in memory and never persisted.


BI dashboard and approval workflow
- Routes:
    GET /bi                          static dashboard (no JS deps)
    GET /filtertrack/bi/auth         role check (user/admin keys)
    GET /filtertrack/bi/overview     summary + flow aggregates
    CSV exports for sessions and samples, JSON export for full sessions.
- Two roles, gated by env vars FILTERTRACK_USER_KEY / FILTERTRACK_ADMIN_KEY:
    user  — view, filter (date/device/filter), download, propose edits / custom filters.
    admin — also approve or reject proposals.
- Approved session edits update the stored session/device/filter facts.
- Approved custom filters appear in the approved custom filters list.
- Tables added: change_proposals, approved_filters (same SQLite DB on /data).

Flow analytics (computed at query time from compact samples + filter area)
- Sign convention matches Android: distance down = water level up = positive L/min;
  distance up = descending = negative L/min.
- Charts on /bi:
    Average Net Flow By Filter (L/min)
    Flow Direction By Filter
    Daily Flow Trend
    Samples By Station
- Sessions CSV adds: flowAvailable, flowLpm, flowDirection,
  distanceStartCm, distanceEndCm, distanceChangeCm.

Non-interactive flyctl auth (no browser, no user intervention)
- Why: ~/.fly/config.yml was wiped to null bytes once already (2026-04-27), forcing
  an interactive `flyctl auth login`. A token in env or a tokens file removes that.
- One-time setup by user (run interactively, just once):
    flyctl tokens create deploy -a filtertrack-api -x 8760h    # 1-year deploy token
  Copy the printed token (starts with "FlyV1 fm2_...").
- Two ways to use the token afterwards. Pick one:

  (A) Per-shell env var (simplest; persists across reboots on Windows):
      setx FLY_API_TOKEN "FlyV1 fm2_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx"
      # then re-open shell. flyctl will pick it up automatically.
      # Verify:  flyctl auth whoami   (will say the token is valid for filtertrack-api).

  (B) Project-local file flyctl reads on demand (gitignored):
      Save token to:  C:\Users\Isaque\AndroidStudioProjects\FilterTrack\backend-fastapi\.fly.token
      Add ".fly.token" to .gitignore.
      Run deploys as:
        set /p FLY_API_TOKEN=<.fly.token && flyctl deploy --app filtertrack-api
      (bash equivalent: FLY_API_TOKEN="$(cat .fly.token)" flyctl deploy --app filtertrack-api)

- Notes:
  * FLY_API_TOKEN takes precedence over ~/.fly/config.yml, so the corrupt-config
    failure mode cannot block deploys when the env var is set.
  * Deploy tokens are scoped to one app — safer than a full personal token from
    `flyctl auth token`. Rotate with `flyctl tokens revoke` when the laptop changes.
  * NEVER commit the token. Treat it like a password.
